# Architecture

## The flow of one order

```text
POST /api/orders
 gateway ──POST /orders──> orders
                            ├─ GET /items/{id}  (once per distinct item)  ──> menu         (price, availability)
                            ├─ save order as `pending`                    ──> memory or PostgreSQL
                            ├─ POST /charge                               ──> payments     (approve or decline)
                            ├─ save `paid` or `payment_failed`
                            └─ POST /notify                               ──> notifications (best effort)
```

Order status: `pending` (saved, not charged yet) → `paid` | `payment_failed` (card declined) | `payment_error` (payments unreachable or failing). A `pending` order that stays `pending` means `orders` died between the two steps.

## Decisions

| Decision | Why |
|----------|-----|
| Synchronous HTTP between services | Easy to see, trace and break. A queue would hide the call chain that students are meant to observe. Pollie (weeks 4-5) already teaches queues. |
| One shared skeleton (`common/app.py`) | Every service gets health, readiness, metrics, request ids, tracing and failure injection identically. Consistency is what makes dashboards and alerts reusable. |
| Liveness without dependencies, readiness with | Standard Kubernetes practice. A failing dependency must not cause restart loops. |
| Timeouts everywhere | A call without a timeout turns one slow service into a full outage. `DOWNSTREAM_TIMEOUT` (default 2 s), payments 5 s, gateway to orders 10 s. |
| Gateway maps failures to 502/503/504 | Callers learn *what kind* of failure it was. |
| Notifications are best effort | A message that cannot be sent must not undo a paid order. |
| Memory store by default | Starts with nothing installed. It also makes the case for a database when you run two replicas. |
| Per-app metrics registry | Five services can run in one process (tests) without duplicate metrics. |
| Plain SQL, no ORM | Every query can be read in one file. |

## Cross-cutting

- **Request id**: taken from `X-Request-ID` or generated by the first service, returned in the response, passed to every downstream call and written to every log line.
- **Tracing**: FastAPI and httpx are instrumented, so spans are created automatically and the `traceparent` header travels between services. The `health`, `ready` and `metrics` endpoints are not traced.
- **Failure injection**: `Chaos` in `common/chaos.py` is consulted by the middleware before the request is handled.

## What is deliberately simple

No authentication, no real payments, no retries or circuit breakers, no message broker, notifications only in memory. Real systems need them; adding them is a good exercise and none of them is needed for the DevOps work around the application.
